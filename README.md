# claude-code-turn-recovery

Claude Code が**レートリミットなどの API エラーでターンを打ち切られたとき、そこで
失われた作業を記録し、次のセッションの冒頭で「何を再開すべきか」を提示する**ための
最小構成サンプルです。

自分のプロジェクトの `.claude/` にそのまま組み込めるよう、hook・設定・テストをまとめて
あります。

> [!IMPORTANT]
> **先に `claude --continue` を試してください。**
> サブエージェントのトランスクリプトは[セッション内で永続化され](https://code.claude.com/docs/ja/sub-agents#resume-subagents)、
> Claude Code を再起動しても同じセッションを再開すれば、`SendMessage` で
> **全履歴を保ったまま**止まった場所から再開できます。多くの場合、これで足ります。
> このハーネスが要るのは、`/clear` した後や新しいセッションで仕切り直したときなど、
> **同じセッションを再開しない**場合だけです。

## 解きたい問題

サブエージェントを並列で走らせていると、usage limit に当たった瞬間にそれらは道半ばで
殺されます。消費済みのトークンは戻りません。**問題はその後です。**

| 起きること                                               | 何が困るか                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------- |
| 同じセッションを再開せず、新しいセッションで作業を続ける | 前のセッションのサブエージェントには `SendMessage` が届かない |
| 何が終わっていて何が終わっていないかが、どこにも残らない | 完了済みの作業まで流し直し、同じトークンを 2 回払う           |
| 制限に当たった直後は CLI ごと落ちる。再開は数時間後      | 人間の側も「何を頼んでいたか」を忘れている                    |

したがってこのハーネスの目標は、**「制限に当たらないようにすること」ではありません**。
当たった後の最初のターンで、何が失われて何が残っているかを Claude 自身が分かるように
して、**同じ作業の流し直しを避けること**です。

- 中断を捕まえるのは `StopFailure`
- 記録を読ませるのは `SessionStart`
- 「誰が走っていたか」を判定する材料を作るのは `PostToolUse`(`Agent`)と `SubagentStop`

この 2 系統を分けるのは好みではなく、仕様上の制約です(後述)。

## ファイル構成

```text
.claude/
├── hooks/
│   ├── agent-call-record.sh      # PostToolUse(Agent): 起動を .call.json に記録
│   ├── agent-call-complete.sh    # SubagentStop:       完了を .done.json に記録
│   ├── turn-failure-record.sh    # StopFailure:        中断を recovery/ に記録
│   ├── session-start.sh          # SessionStart:       再開ブリーフィングを注入
│   ├── recovery-state-gc.sh      # UserPromptSubmit:   古い状態を掃除
│   └── pending_agents_shared.py  # 「未完了」判定の2パス走査(共有モジュール)
├── agents/
│   └── investigator.md           # 途中成果をノートに残すエージェント定義の例
├── tests/                        # hook 自体のテスト(unittest / 外部依存なし)
└── settings.json                 # 上記5つの hook の登録

examples/simulate-interruption.sh # 中断→再開の流れを手元で再現する
docs/design-notes.md              # この設計に至った経緯(素朴に作ると壊れる5箇所)
```

実行時に生成される状態ディレクトリは 3 つです。いずれもコミット対象ではありません。

```text
.claude/agent-calls/<session_id>/<prompt_id>/<agent_id>.call.json   # 起動
.claude/agent-calls/<session_id>/<prompt_id>/<agent_id>.done.json   # 完了
.claude/recovery/<session_id>.json                                  # 中断記録
.claude/agent-notes/*.md                                            # 途中成果
```

## しくみ

```text
[Agent 呼び出し]
      │  PostToolUse (matcher: Agent)
      ▼
agent-call-record.sh
  tool_input.prompt と tool_response.agentId を紐付けて .call.json を書く
      │
      │  ……サブエージェントが完了すれば SubagentStop
      │    agent-call-complete.sh が .done.json を書く
      │
      │  ここで rate_limit / overloaded などに当たる
      ▼
turn-failure-record.sh (StopFailure)
  .call.json はあるが .done.json が無いものを「未完了」として集める
  → 中断理由・ブランチ・未完了/完了済みエージェントを recovery/<session>.json へ
     原子的に書き出す(stdout も終了コードも無視されるので、書くだけ)
      │
      │  数時間後、セッションを開き直す
      ▼
session-start.sh (SessionStart)
  記録を読んで Markdown のブリーフィングを stdout に出す
  → stdout はそのまま Claude のコンテキストに入る
  → 出したら .json.consumed へ改名(二度は出さない)
      │
      ├─ 記録がある ─▶ 未完了エージェントの一覧 + 再開手順 1〜4
      │
      └─ 記録が無い ─▶ 台帳をセッションまたぎで走査し、
                       「走ったまま終わった」エージェントを拾う
                       (サブエージェントだけが殺された中断は
                        StopFailure が発火しないため)
```

判定式は 1 つだけです。

> **`.call.json` はあるが、対応する `.done.json` が無い = 中断された瞬間に走っていた
> エージェント**

### なぜ書く側と読ませる側を分けるのか

`StopFailure` の仕様上、**hook にできるのはディスクに書くことだけ**だからです。

| イベント       | stdout                                | 終了コード |
| -------------- | ------------------------------------- | ---------- |
| `StopFailure`  | 無視される(デバッグログのみ)          | 無視される |
| `SessionStart` | **Claude のコンテキストに追加される** | —          |

`StopFailure` はエラーが既に起きた後に発火するので、中断をブロックしたり結果を変えたり
できません。一方 `SessionStart` は stdout がそのままコンテキストに入る数少ないイベントの
ひとつです(他は `UserPromptSubmit` / `UserPromptExpansion`)。

したがって「書く側 = `StopFailure`」「読ませる側 = `SessionStart`」に分け、ディスク上の
JSON で繋ぎます。

### なぜ完了は SubagentStop で捉えるのか

サブエージェントは既定でバックグラウンド実行されるため、`PostToolUse` は**起動が返った
時点**(`tool_response.status == "async_launched"`)で発火します。これを完了の代わりに
使うと、1 メッセージで同時発行した並列呼び出しの 2 本目より前に来てしまい、**並列で
走っている兄弟が互いを完了済みとみなします**。

移植元での実測では、`PostToolUse` は起動の 0.4 秒後、並列呼び出しの間隔は 0.8 秒、
`SubagentStop` は約 6 秒後でした。「完了 = `SubagentStop`」にして初めて、この取り違えが
起きないことが保証されます。

それでも起動側を `PostToolUse` で記録するのは、**`tool_input.prompt` と
`tool_response.agentId` の両方を持つ唯一のイベント**だからです。「どの `agent_id` が
どんな依頼で起動されたか」はここでしか確定できません。

### `StopFailure` の入力

公式ドキュメントによれば、共通フィールドに加えて次の 3 つを持ちます。

| フィールド               | 型     | 内容                                 |
| ------------------------ | ------ | ------------------------------------ |
| `error`                  | string | ターンを終わらせたエラー種別         |
| `error_details`          | string | 追加の詳細(optional)                 |
| `last_assistant_message` | string | 失敗前の最後のメッセージ(optional)   |

`error` に入りうる値は `rate_limit` / `overloaded` / `authentication_failed` /
`oauth_org_not_allowed` / `billing_error` / `invalid_request` / `model_not_found` /
`server_error` / `max_output_tokens` / `unknown` です。

**`matcher` は付けていません。** `rate_limit` に絞りたくなりますが、`overloaded` でも
`server_error` でも「作業が飛ぶ」事情は同じです。全部記録して、区別は読む側に任せます。

`unknown` は正規の値なので、`session-start.sh` は空文字と同じく「原因不明」に読み替えて
から表示します。素通しにすると、日本語のブリーフィングに英語の `(unknown)` が混ざります。

参考: [Hooks リファレンス(公式ドキュメント)](https://code.claude.com/docs/ja/hooks)

## 再開ブリーフィングの中身

`examples/simulate-interruption.sh` が実際に出力するものです。

```text
## 前回ターンの中断記録 (rate_limit)
- 中断の原因になったAPIエラーがまだ続いているかどうかは、この記録からは分からない。
  ただし「まだ制限中かもしれない」はサブエージェントへの委譲を控える理由にならない。
  制限が明けていれば委譲は普通に動くし、明けていなければメインセッションが自分で
  実装しても同じように失敗する
- 中断: 2026-09-04 02:39 / You've hit your session limit · resets 8:40pm (Asia/Tokyo)
- 未完了だったサブエージェント (1件):
    - implementer [agent_implementer] サムネイル生成のキャッシュを追加する
- このターンで完了済み (1件): reviewer [agent_reviewer] — 再実行しない
- 再開の手順 (上から順に試し、成功した時点で次には進まない):
    1. `.claude/agent-notes/` に途中成果が残っていないか先に確認する
    2. 未完了エージェントに SendMessage(to: "<agent_id>") を送って再開する
    3. SendMessage が届かない場合は、残りの作業を新しいサブエージェントに委譲する
    4. メインセッションが自分で実装するのは最後の手段
- 組み込みの Explore / Plan は再開できない
```

意図している点は 4 つです。

- **完了済みも伝える。**「未完了はこれ」だけを渡すと、既に終わったエージェントまで
  念のため走らせ直されます。「再実行しない」を明示します。
- **手順に出口を書く。** `SendMessage` はエージェントが消えていると届きません。
  不達時の出口(手順 3)が無いと、消去法で「自力実装」が唯一の選択肢になります。
- **鮮度を添える。** 呼び出しから 1 時間を超えたエージェントには `(古い)` を付けます。
- **切り捨てを見せる。** 記録側 12 件・表示側 8 件で切りますが、切る前の総数も
  記録して `(他 N 件、上限により省略)` と出します。

## サブエージェント側の準備(hook だけでは埋まらない穴)

hook が記録できるのは「**誰が**走っていたか」までです。「そのエージェントが**何を掴んで
いたか**」は本人しか知りません。API エラーで打ち切られたサブエージェントは最後の出力を
親に返しますが([公式ドキュメント](https://code.claude.com/docs/ja/sub-agents#api-errors-in-subagents))、
親のターンごと落ちればそれも次のセッションには残りません。

そこで、エージェント定義そのものに途中成果の保全を書きます
(`.claude/agents/investigator.md` が例です)。

```markdown
## 途中成果の保全

調査が数分を超えそうなら、確定した所見をその都度
`.claude/agent-notes/<YYYYMMDD>-investigator-<短いスラッグ>.md` に追記する。

- なぜ: レート制限などのAPIエラーで打ち切られると、親に渡るのは最後の1発言だけ。
- ノートの1行目に依頼の1行要約を書く。中断記録と突き合わせるための目印になる。
- 追記は `cat >> <パス> <<'EOF'` で行う。**書いてよいのは自分のノートだけ**で、
  ソースツリーは読み取り専用のまま。
```

読み取り専用エージェントに書き込みを許すのは一見矛盾しますが、**書いてよい場所を自分の
ノートだけに限定**することで、ソースツリーの読み取り専用性は保たれます。

再開手順の 1 が「まずノートを見る」なのはこのためです。ノートが残っていれば、
`SendMessage` が届かなくても「どこまで終わっていて、次に何をするか」を書いた**新しい
指示**を作れます。前回の依頼文を丸写しするのではなく、差分だけを渡します。

## 設計上の勘どころ

素朴に実装すると動いているように見えますが、実際には静かに壊れます。以下はすべて実運用で
踏んだ問題への対処です。詳細と再現条件は [設計記録](./docs/design-notes.md) にあります。

### 完了判定はセッション全体で行う

バックグラウンドのサブエージェントは**ユーザーの発言をまたいで生き続ける**ため、
`.call.json`(起動時の `prompt_id`)と `.done.json`(完了時の `prompt_id`)は日常的に
別ディレクトリになります。同じ `prompt_id` の中だけで突き合わせると、**完了済みの
エージェントが軒並み未完了に化けます**。

`collect_done_keys()` がセッション配下の全 `prompt_id` を舐めているのはこのためです。

### 同じ判定を 2 箇所に持たない

上記の修正が `session-start.sh` 側にしか入らず、`turn-failure-record.sh` が
`prompt_id` スコープのまま取り残されて、**いま走っているエージェントが pending から
脱落する**退行が起きました。2 箇所が食い違ってもエラーは出ません。件数が変わるだけです。

いまは 2 パス走査を `pending_agents_shared.py` に集約しています。逆に、**対象セッションの
選び方は共有していません**。`turn-failure-record.sh` は現在のセッションだけを見て、
`session-start.sh` は現在のセッションを除く全セッションを見る、というちょうど裏返しの
関係だからです。

### 上限で切る前に、何の順で並んでいるかを確認する

`prompt_id` は UUID で、**発行順とは無関係**です。`os.listdir()` の辞書順のまま 12 件で
切ると、たまたま辞書順で後ろに来た `prompt_id` にいる「いま走っているエージェント」が
枠から漏れます(古い `prompt_id` に 15 件、現在の `prompt_id` に 1 件、という配置で
実際に脱落しました)。呼び出し時刻の降順に並べてから切ります。

### サブエージェントだけが殺される中断は StopFailure が発火しない

レート制限は、サブエージェントだけを殺してメインのターンを生かすことがあります。この場合
ターンは正常終了扱いになり、中断記録は作られません。そのままセッションが終わると、走りかけの
サブエージェントの存在は次のセッションに伝わりません。

`session-start.sh` は、中断記録が**無いときに限り**台帳をセッションまたぎで走査して
この穴を埋めます(記録があるときは二重に出しません)。

### 共有される主データに、片方の読み手の都合の状態を混ぜない

「一度提示したら二度出さない」印を、当初は `.call.json` 自体のリネームで実現していました。
しかし `.call.json` は複数の hook が共有で読む**台帳の主データ**です。中断記録の
`.json` → `.json.consumed`(消費したら役目が終わる通知)とは性質が違います。

実害が出ていなかったのは、孤児スキャンが現在のセッションを除外していたからで、偶然です。
`--resume` で古いセッションを開き直した瞬間に、提示済みのものだけが黙って見えなくなります。
いまは主データを変更せず、サイドカーの `.presented.json` を別に置いています。

### ハーネスが注入する文言に、検証できない断定を混ぜない

初期のブリーフィングには「この記録が出ている = 中断の原因になった API エラーは既に
解消している」と書いていました。**成立しません。** `SessionStart` hook はローカルで走り、
API リクエストの成功を前提にしません。制限中でも CLI は起動でき、ブリーフィングは
注入されます。

そして、これはハーネスが毎セッション自動で注入する文言です。**モデルにはそれを疑う手段が
ありません。** いまは事実主張だけを削り、行動指示は残しています。行動指示は事実主張に
依存せずに書けます。

### 状態は必ず GC する

`recovery-state-gc.sh` が `UserPromptSubmit` で 7 日より古いものを掃除します。中断記録も
ノートも、7 日経てば再開の役には立ちません。`-name` で対象を絞っているのは、同じ場所に
置いた無関係なファイルを巻き込まないためです。

なお**提示の条件(24 時間)と GC の保持期間(7 日)は別物**です。24 時間を過ぎた中断は
「別の作業の話」として提示しませんが、ファイルは調査用に残ります。

## 導入手順

### 1. 自分のプロジェクトに組み込む

`.claude/hooks/` と `.claude/settings.json` を自分のリポジトリにコピーし、hook に実行権限を
付けます。

```bash
cp -r .claude/hooks .claude/settings.json <your-project>/.claude/
chmod +x <your-project>/.claude/hooks/*.sh
```

実行時に生成される状態ディレクトリはコミット対象ではないので、`.gitignore` に追加して
ください。

```text
.claude/agent-calls/
.claude/recovery/
.claude/agent-notes/
```

すでに `.claude/settings.json` がある場合は、5 つの hook のエントリをマージします。
このハーネスはプロジェクト固有の設定を持たないので、**conf を書き換える作業はありません**。

### 2. サブエージェント定義に「途中成果の保全」を足す

`.claude/agents/investigator.md` の該当セクションを、自分のエージェント定義にコピーします。
hook だけでは「そのエージェントが何を掴んでいたか」を救えないので、ここが対になります。

### 3. hook のテストを実行する

外部依存はありません。`uv` でも素の `python3` でも動きます。

```bash
python3 -m unittest discover -s .claude/tests -t .claude/tests -v
# または
uv run python -m unittest discover -s .claude/tests -t .claude/tests -v
```

### 4. 動作を手元で確かめる

本物のレート制限を待たずに、中断から再開までの流れを再現できます。実運用と同じ hook を
使い、状態ディレクトリだけを一時ディレクトリに向けます。

```bash
bash examples/simulate-interruption.sh
```

3 本のサブエージェントを起動し、うち 2 本を完了させ、中断を起こしてブリーフィングを
出すところまでを通します。それぞれ確認したい性質が違います。

| エージェント         | 何が起きるか                | 確認できる性質                         |
| -------------------- | --------------------------- | -------------------------------------- |
| `agent_investigator` | 別の `prompt_id` で完了     | セッション全体での突き合わせが効く     |
| `agent_reviewer`     | 同じ `prompt_id` で完了     | 「再実行しない」として併記される       |
| `agent_implementer`  | 完了しないまま中断          | 再開すべき対象として提示される         |

## 設定できる環境変数

いずれも既定値で動きます。テストとトラブルシュート用です。

| 環境変数                     | 既定値                     | 用途                                     |
| ---------------------------- | -------------------------- | ---------------------------------------- |
| `TURN_RECOVERY_STATE_DIR`    | `.claude/recovery`         | 中断記録の置き場                         |
| `AGENT_CALLS_STATE_DIR`      | `.claude/agent-calls`      | 台帳の置き場                             |
| `AGENT_NOTES_DIR`            | `.claude/agent-notes`      | 途中成果ノートの置き場(GC 対象)          |
| `TURN_RECOVERY_TTL_SEC`      | `86400`(24h)               | 中断記録を提示する期限                   |
| `TURN_RECOVERY_CALL_TTL_SEC` | `86400`(24h)               | `.call.json` の鮮度判定                  |
| `HOOK_STATE_GC_DAYS`         | `7`                        | 状態ファイルの保持日数                   |
| `TURN_RECOVERY_DISABLE`      | —                          | `1` で中断記録を無効化                   |
| `AGENT_CALLS_DISABLE`        | —                          | `1` で台帳の記録を無効化                 |

`settings.json` の `env` には、被害そのものを減らす設定も入れています。

- **`CLAUDE_AUTO_BACKGROUND_TASKS=1`**: 約 2 分を超えたサブエージェントを自動で
  バックグラウンドへ移します。バックグラウンドは API エラーで失敗しても最後の出力が親に
  渡るのに対し、**まだ何も出力していないフォアグラウンド**のサブエージェントだけは
  `Agent terminated early due to an API error` で中身ごと失われます(v2.1.200 以降)。
  v2.1.198 以降はバックグラウンドが既定ですが、Claude が結果を待つ判断をした場合の保険です。
- **`CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY=6`**: 並列実行の上限を下げ、1 回の中断で
  巻き添えになる作業を減らします。下げすぎると通常の調査が目に見えて遅くなります。
  なお**この変数は公式ドキュメントに記載がありません**。無くても動作します。

## 既知の限界

- **記録できるのは「誰が走っていたか」まで。** 中身は救えません。だから
  `.claude/agent-notes/` への途中成果の書き出しが対になります。
- **`agent_id` が取れない起動は記録されません。** `.done.json` と紐付けられないため、
  黙って諦めます(誤った未完了を作るより、記録しないほうを選んでいます)。
- **組み込みの `Explore` / `Plan` は one-shot で再開できません。** ブリーフィングは
  そのことを明記しますが、ハーネス側で再開可能にはできません。長引きそうな作業は
  再開できるカスタムエージェントに投げてください。
- **サブエージェント内部の中断は捕捉できません。** 捉えているのはメインのターンが
  打ち切られた場合(`StopFailure`)と、`SubagentStop` が来ないまま終わった場合の 2 つです。
- **失敗は沈黙で表れます。** すべての hook が fail-open(何が起きても `exit 0`)なので、
  記録に失敗しても何も通知されません。テストが厚めなのはこのためです。

## 必要環境

- **Claude Code 2.1.78 以降**(下表参照。実挙動は 2.1.199 以降を推奨)
- bash
- Python 3(hook 内の JSON 解析とテストに使用。追加パッケージ不要)
- git(中断時のブランチ記録に使用。無くても動作する)

このハーネスは `StopFailure` だけでは成立しません。次の機能がすべて揃って初めて動きます
(バージョンは [Claude Code の CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) より)。

| バージョン | 追加されたもの                                                   | ここでの役割                                       |
| ---------- | ---------------------------------------------------------------- | -------------------------------------------------- |
| 1.0.41     | `Stop` から `SubagentStop` を分離                                | サブエージェントの完了だけを単独で捉えられる       |
| 2.0.42     | `SubagentStop` に `agent_id` / `agent_transcript_path`           | 完了記録を `agent_id` で紐付けられる               |
| 2.1.47     | `Stop` / `SubagentStop` に `last_assistant_message`              | 完了時の最終報告をトランスクリプト解析なしで残せる |
| 2.1.77     | Agent の `resume` を廃止し `SendMessage({to: agentId})` に一本化 | 中断したサブエージェントを `agent_id` で再開できる |
| 2.1.78     | `StopFailure`                                                    | 中断の瞬間そのものを検知できる                     |
| 2.1.98     | 失敗したバックグラウンドサブエージェントが部分的な進捗を親に報告 | 長い作業をバックグラウンドに置く判断が成り立つ     |
| 2.1.199    | API エラーで打ち切られたサブエージェントが部分成果を親に報告     | 中断時に拾えるものが「無」ではなくなった           |

**再開の口(`SendMessage`)と中断の検知(`StopFailure`)は隣り合ったバージョンで揃いました。**
片方だけでは足りません。中断を検知できても再開する手段が無ければ記録は活かせませんし、
再開できても何を再開すべきか分からなければ意味がないためです。

設計の背景と経緯は [docs/design-notes.md](./docs/design-notes.md) にまとめています。
