# 中断記録ハーネスの設計記録 — 素朴に作ると壊れる5箇所

このリポジトリのロジックは、個人開発の Python プロジェクトで実際に運用していた
中断記録ハーネスを汎用化したものです。この文書は、その設計根拠を、プロジェクト固有の
情報を取り除いて転記したものです。

素朴に実装したときに動いているように見えて実際には壊れている箇所を、実運用で 1 つずつ
踏んで直しました。以下はすべて、その修正の記録です。**このハーネスの失敗は例外ではなく
沈黙で表れます**(「未完了が 0 件でした」と「未完了の検出に失敗しました」が
区別できない)。だから素朴な実装で壊れていても気付けません。

- 対象: `agent-call-record.sh` / `agent-call-complete.sh` / `turn-failure-record.sh` /
  `session-start.sh` / `pending_agents_shared.py`
- 位置づけ: 実施済みの変更の根拠記録

---

## 1. 完了判定を prompt_id 単位でやると、完了済みを未完了と誤認する

### 何をしていたか

`.call.json` と `.done.json` の突き合わせを、**同じ `prompt_id` ディレクトリの中だけ**で
行っていました。状態が `<session_id>/<prompt_id>/` に分かれているので、素直な設計に
見えます。

### なぜ壊れたか

サブエージェントは既定でバックグラウンド実行され、**ユーザーの発言をまたいで生き続けます**。
起動時の `prompt_id` と完了時の `prompt_id` は日常的に別物になります。同じ `prompt_id` の
中だけを見ると、既に完了しているエージェントが軒並み「未完了」に化けます。

再開ブリーフィングに完了済みのエージェントが並ぶと、そのぶんだけ同じ作業が流し直され、
**中断で失ったトークンをもう一度払う**ことになります。ハーネスが解こうとしていた問題を、
ハーネス自身が作り出していました。

### どう直したか

`.done.json` の集約範囲を**セッション全体**に広げました。`collect_done_keys()` が
セッション配下の全 `prompt_dir_names` を舐めているのはこのためです。

回帰テスト: `test_pending_agents_shared.py::test_done_in_other_prompt_dir_clears_pending` /
`test_turn_failure_record.py::test_done_in_earlier_prompt_id_is_not_pending`

## 2. 同じ判定が 2 箇所にあると、片方だけ直して食い違う

### 何をしていたか

未完了判定を `turn-failure-record.sh`(中断記録を書く側)と `session-start.sh`
(孤児を走査する側)がそれぞれ独立に実装していました。

### なぜ壊れたか

上記 1 の修正が `session-start.sh` 側にしか反映されませんでした。
`turn-failure-record.sh` は `.call.json` 側が現在の `prompt_id` スコープのまま
取り残され、**いま走っているエージェントが pending から脱落する**退行が生まれました。

2 箇所が食い違っても、どちらもエラーを出しません。出力の件数が変わるだけです。

### どう直したか

2 パス走査(パス 1: `done_keys` の集約、パス 2: `.call.json` の未完了抽出、TTL 鮮度判定)を
`pending_agents_shared.py` に切り出し、両方の hook が import して共有します。

意図的に共有していないものもあります。

| 関心事                 | turn-failure-record.sh   | session-start.sh                 |
| ---------------------- | ------------------------ | -------------------------------- |
| 対象セッション         | 現在の session_id のみ   | 現在の session_id を**除く**全部 |
| 並べ替え               | 呼び出し時刻の降順       | 呼び出し時刻の降順               |
| 件数上限               | 12 件(記録)              | 8 件(表示)                       |

対象セッションの選び方がちょうど裏返しになっているのがポイントです。共有モジュールに
持たせるのは「2 パス判定そのもの」だけで、誰を対象にするかは呼び出し側の判断です。

## 3. UUID の辞書順で切り捨てると、本命が枠から漏れる

### 何をしていたか

記録する未完了エージェントは 12 件を上限にしています。これを `os.listdir()` の
ソート順、つまり **`prompt_id` の辞書順**のまま切っていました。

### なぜ壊れたか

`prompt_id` は UUID です。**発行順とはまったく無関係**なので、辞書順で後ろに来た
`prompt_id` に「いま本当に走っているエージェント」がいると、上限に押し出されて落ちます。

再現条件は次のとおりです。

- 古い `prompt_id` に未完了の `.call.json` を 15 件
- 現在の `prompt_id` に本当に走っていた呼び出しを 1 件
- 現在の `prompt_id` が辞書順で後ろに来る配置

この配置で、live な呼び出しが pending から完全に脱落しました。

### どう直したか

**呼び出し時刻の降順**に並べてから切ります。`time` が無い/不正なレコードは最も古い
扱いです。あわせて、切り捨てる前の総数(`pending_total`)も記録し、
再開ブリーフィングで `(他 N 件、上限により省略)` と出します。**上限が黙って情報を
落とすのを避ける**ためです。

回帰テスト: `test_turn_failure_record.py::test_newest_calls_survive_the_cap`

## 4. サブエージェントだけが殺されると StopFailure が発火しない

### 何が抜けていたか

レート制限は、**サブエージェントだけを殺してメインのターンを生かす**ことがあります。
メインが生きているのでターンは正常終了扱いになり、`StopFailure` は発火しません。
つまり中断記録が作られません。

その場でメインが気付けば `SendMessage` で再開できますが、気付かないままセッションが
終わると、走りかけのサブエージェントの存在は次のセッションに一切伝わりません。

### どう直したか

`session-start.sh` に**フォールバック走査**を足しました。中断記録が「無い」ときに限り、
`agent-calls/` の台帳を**セッションをまたいで**直接走査します(`find_orphan_agents()`)。
現在の `session_id` は除外します — まだ生きている可能性があるためです。

中断記録が有るときはこの経路に入りません(二重に出さない)。

回帰テスト: `test_session_start.py::OrphanAgentTests`

## 5. 共有される主データに、片方の読み手の都合の状態を混ぜない

### 何をしていたか

孤児走査には「一度提示したら二度出さない」印が要ります。中断記録のほうは
`.json` → `.json.consumed` へのリネームでやっていたので、同じ考え方で
`.call.json` → `.call.json.presented` とリネームしていました。

### なぜ良くないか

`.call.json` は**複数の hook が共有で読む台帳の主データ**です。中断記録の `.json` が
「消費したら役目が終わる通知」なのとは性質が違います。

当時実害が出ていなかったのは、孤児スキャンが現在のセッションを除外していて、他の hook は
現在のセッションしか見ていなかったからです。偶然です。次のどちらかが起きた瞬間に、
**提示済みのものだけが黙って見えなくなります**。

- どれかの hook がセッションをまたいで `.call.json` を読むようになる
- `--resume` で古いセッションを開き直す(そのセッションの `.call.json` は既に
  リネームされていて `turn-failure-record.sh` から見えない)

### どう直したか

主データは変更せず、サイドカーの `.presented.json` を別に置きます。
`recovery-state-gc.sh` はセッションディレクトリごと `rm -rf` するので、入れ子の
サイドカーも一緒に回収されます。

回帰テスト: `test_session_start.py::test_presented_marker_is_a_sidecar_not_a_rename`

## 6. ハーネスが注入する文言に、検証できない断定を混ぜない

これは実装バグではなく**文章のバグ**ですが、影響は同じかそれ以上です。

### 何を書いていたか

再開ブリーフィングに、こう書いていました。

> この記録が出ている = 新しいセッションが開始できている = 中断の原因になった
> API エラーは既に解消している

### なぜ良くないか

成立しません。`SessionStart` hook は**ローカルで走り**、モデルへの API リクエストが
成功したことを前提にしません。制限中でも CLI は起動でき、その時点でブリーフィングは
注入されます。

そして、これはハーネスが**毎セッション自動で注入する**文言です。モデルにはそれを疑う
手段がありません。検証不能な事実主張を、権威ある前提として毎回渡していたことになります。

### どう直したか

事実主張だけを削り、行動指示は残しました。

> 中断の原因になった API エラーがまだ続いているかどうかは、この記録からは分からない。
> ただし「まだ制限中かもしれない」はサブエージェントへの委譲を控える理由にならない。
> 制限が明けていれば委譲は普通に動くし、明けていなければメインセッションが自分で
> 実装しても同じように失敗する

**行動指示は事実主張に依存せずに書けます。**「制限は明けている**から**委譲してよい」
ではなく、「明けていてもいなくても自力実装に利点はない**から**委譲する」と書けば、
前提が崩れても指示は生き残ります。

回帰テスト: `test_session_start.py::test_does_not_claim_the_limit_has_lifted`

## 付録: 再開手順に「出口」を書く

未完了エージェントがあるとき、ブリーフィングは 1〜4 の順序付きの手順を出します。

初期版は 1・2 だけでした(ノートを見る → `SendMessage` で再開する)。しかし
`SendMessage` はエージェントが既に消えていると届きません。**不達時の出口が無いと、
消去法で「メインセッションが自分で実装する」が唯一の選択肢になります。**

そこで 3(新しいサブエージェントへ委譲する。ただし前回の依頼文を丸写しせず、ノートを
踏まえた差分の指示を渡す)と 4(自力実装は最後の手段)を明記しました。

同じ理由で、組み込みの `Explore` / `Plan` が one-shot で再開できないことも書いています。
再開できないエージェントに委譲していると、この手順の 2 が最初から使えません。
